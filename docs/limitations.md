# 已知限制

本文件如实记录首版的边界与未验证项。PLAN 明确规定：**任何市场缺少必要数据权限或无法访问，
作为首版发布阻塞项处理，不用演示数据替代验收。**

---

## 一、尚未验证的阻塞项

### 1. 四数据源的真实权限与可达性（M0 出口条件）

所有适配器都只针对**固定响应样本**做过自动化测试（`tests/test_adapters.py` 使用 httpx MockTransport），
尚未在真实凭证与真实网络下运行。以下均为待验证项：

| 市场 | 数据源 | 待验证 |
|---|---|---|
| 美股 | Alpaca IEX | key/secret 权限、`feed=iex` 是否可用、快照与 bars 接口返回结构、限流阈值 |
| A 股 | Tushare | 积分是否覆盖 `daily` + `stk_limit` + `adj_factor` 三个接口、单次调用配额 |
| 加密 | Coinbase Exchange | 本机网络可达性、`/products/{id}/book` 与 `/candles` 限流 |
| 预测 | Polymarket | Gamma `clob_token_ids` 查询、CLOB `/book` 与 `/prices-history`、UMA 结算状态字段 |

**Tushare 尤其需要注意**：`stk_limit`（涨跌停）与 `adj_factor`（复权因子）通常需要较高积分。
权限不足时适配器会显式抛出 `Tushare permission or query error (<code>)`，
该市场应标记为阻塞而不是已交付。

### 2. 五个交易日运行观察

PLAN §四 要求正式发布前完成至少 5 个股票交易日的运行观察，覆盖四市场数据更新、AI 决策与交易链路。
**尚未执行。**

### 3. Polymarket 自然结算

`core.settle()` 与 `worker.poll_resolutions()` 已实现，但从未在真实市场结果确认下运行。
PLAN 要求用确定性历史样本验证结算，不依赖观察期内恰好出现自然结算。**尚未执行。**

### 4. 恢复能力演练

以下场景 PLAN §四 第 8 项要求覆盖，**均未演练**：
断网、数据库短暂不可用、worker 崩溃、本机休眠、备份恢复后不重放旧订单。

## 二、行情数据的固有限制

### 美股：单一交易所覆盖

Alpaca 免费档使用 `feed=iex`，**只覆盖 IEX 一个交易所**的报价，不是全市场综合报价（SIP）。
后果：

- 买卖价可能与你在券商看到的价格不同
- 盘口深度（`bid_size`/`ask_size`）显著小于真实全市场深度，撮合数量因此偏保守
- 快照 `source` 字段固定标注 `Alpaca IEX (single venue)`，界面原样展示

页面会显示这一覆盖范围，不会伪装成全市场数据。

### A 股：日线低频模拟

A 股**没有盘中数据**，只有收盘后的日线。因此：

- 决策在每个新交易日的日线批次做一次
- 订单等待**下一根完整日线**到达后才成交，以该交易日**开盘价**加费用与滑点模型估算
- 不支持盘中限价成交推断（限价单在 A 股被 schema 直接拒绝）
- 成交量参与率上限设为当日成交量的 **0.1%**，这不是对开盘集合竞价流动性的断言，
  只是为了避免日线模式下假设无限流动性
- `simulated_at`（行情事件时间）与 `processed_at`（本机实际处理时间）会跨日，界面分别展示

代码中所有 A 股成交都标注为日线模拟假设。**决策当天的已知收盘价不会用于成交**
（`tests/test_core.py` 覆盖同快照不成交；`match()` 要求 `q.data['session'] > original.data['session']`）。

### 公司行动与交易状态

- 美股：用「当日开盘价 vs 前收盘价偏离 > 25%」保守识别未调整的价格跳变，
  命中即置 `corporate_action_safe=False` 并暂停该标的交易，提示需要人工复核。
  **不会自行推算复权调整。**
- A 股：比较相邻两日 `adj_factor` 是否一致；首根历史 bar 无前值可比，
  一律标为未验证（不参与成交），属刻意的保守处理。
- 拆股、分红、送转等无法可靠处理的情形下，标的可能长期停留在暂停状态，需要人工介入。

### 延迟与新鲜度

- 各供应商的延迟由接口决定，`delay_seconds` 原样记录并在界面展示
- 非 A 股市场的报价超过 `delay_seconds + 120` 秒即判定过期，阻塞新单
- A 股的新鲜度按交易日历判断：正常的隔夜、周末与节假日**不会**被认定为断流
- 估值与执行使用两套判定：收盘后的最后一笔收盘价对**记账**仍然有效，
  但会阻塞**新单执行**

## 三、交易与撮合模型的限制

| 限制 | 说明 |
|---|---|
| 仅模拟 | 无真实下单、无钱包签名、无链上交易能力；所有订单与资金均为虚拟 |
| 无杠杆、无做空 | 卖出不能超过可卖持仓；A 股还需满足 T+1 |
| 品种范围 | 美股普通股、沪深主板普通股、BTC/ETH 现货、二元预测市场。期权、期货、融资融券、科创板/创业板/北交所、非二元市场均不支持 |
| 订单类型 | 市价、限价、撤单、部分成交。无止损、无OCO、无冰山等高级类型 |
| 预测市场 | 只支持 Yes/No 二元市场，Yes 与 No 是独立持仓；多结果市场被显式拒绝 |
| 流动性 | 有盘口时按盘口限量；无盘口回落到成交量。数据不足时不假设无限流动性 |
| 过期 | 非 A 股订单 24 小时过期，A 股订单 10 天过期 |

## 四、跨币种报表

- 折算汇率需**用户手工录入并带时间戳**，没有自动汇率源
- 汇率超过 `fx_max_age_hours`（默认 168 小时）后：
  - 组合估值不再展示为单一 USD 数字，改为分币种展示
  - 依赖统一估值的组合风险判断与新单被阻断（`FX stale or invalid`）
- 汇率**只影响报表与风险估值，不改变原生账本**；各市场账本始终以其记账币种记录
- 组合估值使用单一 `fx_cny_per_usd`，不支持随时间变化的历史汇率序列

## 五、AI 与策略的限制

| 限制 | 说明 |
|---|---|
| 不执行任意生成代码 | AI 只能输出 `hold` / `order` / `strategy` 三种结构化动作，经 JSON Schema + Pydantic 双层校验 |
| 策略是白名单参数 | 仅 trend / mean_reversion / probability 三个模板，指标与参数有界；AI 不能修改风控、密钥、数据库或撮合实现 |
| 无自动汇率、无归因分析 | 属后续版本 |
| 评估深度依赖历史补齐 | `evaluate_series` 要求 ≥ `min_samples × 2`（默认 120）条快照。历史补齐失败（如 Tushare 权限不足）时策略会长期停留在 candidate，**这是刻意行为**，不会降低门槛凑发布 |
| 预测市场评估样本 | Polymarket 历史价格点不携带盘口深度，因此回放中无法成交；预测市场策略主要依赖 worker 实时采集的带深度快照累积样本 |
| 模型失败即不下单 | 超时、HTTP 错误、非法 JSON、Schema 校验失败一律记为 `failed` 并记录原因，不会伪装成 `hold`，也不会产生订单 |
| 价格未知时的预算 | 未配置 `input_cost_million`/`output_cost_million` 时费用记为 0，此时仅按调用次数与 token 限额执行 |
| 发布门槛由用户设置 | AI 无权修改评估门槛；不以实现盈利作为软件验收条件 |

## 六、工程与运维的限制

| 限制 | 说明 |
|---|---|
| 单机单用户 | 模块化单体 + 单 worker；无横向扩展设计 |
| 全局运行时锁 | 所有资金变更、设置修改与暂停都串行化在单一 runtime 行锁上。对单人工作负载足够，高并发下会成为瓶颈（可替换为按账户排序加锁） |
| 无 Redis | 后台任务用数据库持久化队列 + 租约 + 幂等键实现 |
| 仅本机访问 | 默认绑定 127.0.0.1，配本机会话令牌与写操作 Origin 校验。**不要**直接对公网暴露 |
| 无 CI | `.github/workflows/` 目前为空；测试需在本地运行（依赖本机 PostgreSQL） |
| 无前端自动化测试 | vitest / testing-library / playwright 已在 devDependencies 中，但尚无用例 |
| 无 OpenAPI 生成类型 | `npm run types` 脚本存在，但 `src/api-types.d.ts` 未生成，前端类型仍多为 `any` |
| bundle 体积 | 前端单包约 725 kB（含 recharts），未做代码分割 |

## 七、明确不在范围内

按 PLAN §五：

- 多用户、云部署
- 任意代码策略
- 真实交易、真实资金、钱包签名、杠杆、做空
- 自动汇率源
- 更多策略类型与归因分析
- 通知渠道
- 付费盘中行情

## 八、数据完整性保证

以下是**已经**由代码与测试保证的不变量（不属于限制，列出以明确边界）：

- 金额与数量一律十进制定点（`Numeric(30,10)`），时间一律 UTC 存储
- 每次成交在同一事务内原子更新订单、现金、持仓、费用与账本
- 禁止负现金与超卖
- `Fill(order_id, snapshot_id)` 唯一约束 + `Ledger.key` 幂等键，重复任务不会重复记账
- 订单不会用生成决策的旧报价立即成交
- `reconcile()` 校验现金 == 账本合计、冻结 == 活跃订单冻结合计、现金 ≥ 冻结 ≥ 0
- 暂停幂等，且推进 epoch 使迟到的 AI 结果失效
